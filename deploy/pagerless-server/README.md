# pagerless-server manifests

A kustomize base that deploys `pagerless-server` into the `pagerless` namespace: the Triage and TriageApproval CRDs, the server's RBAC, the agent service account, the admission webhooks, the Service, and the Deployment.

- **CRDs.** `crds/pagerless.dev_triages.yaml` and `crds/pagerless.dev_triageapprovals.yaml` are generated from `api/` by `make manifests`. Do not edit it by hand.
- **Agent permissions.** The `pagerless-agent` service account is bound to no Role. The agent presents its projected token (audience `pagerless-server`) to the server, and a second projected token (audience: the Keycloak realm issuer) only to Keycloak.
- **Job admission.** The fail-closed `pagerless-server-agent-jobs` admission policy independently limits Jobs created by the server to the unprivileged `pagerless-agent` identity, explicit inference Secret keys, a short-lived report-audience token and a Keycloak realm-audience token, temporary storage, and the dedicated `pagerless-replay-capture` claim. It rejects other Secret references, ServiceAccounts, token audiences, host access, privileged containers, and additional containers. The agent image remains an operator configuration. The capture claim must contain only recordings; using another claim name requires changing both server validation and this policy. Operators with other identities can still deploy the platform and retrieve captures.
- **Webhook TLS.** At every start the server generates a certificate authority and a serving certificate in memory, writes the serving pair to a memory-backed volume, and publishes the authority in the `caBundle` of the `pagerless-server` `ValidatingWebhookConfiguration` and `MutatingWebhookConfiguration`. The webhook configurations are therefore committed with an empty `caBundle`, and a GitOps tool must ignore differences in `/webhooks/*/clientConfig/caBundle`.
- **Images.** The Deployment references `ghcr.io/a-hagi613/pagerless-server` and, through `--agent-image`, `ghcr.io/a-hagi613/pagerless-agent`, both at version `0.1.0`.
- **History and retention.** The server appends a status snapshot to the SQLite file at `--history-path` on every Phase change, and appends each step event as it arrives. The file is on the `pagerless-history` PersistentVolumeClaim, and the schema refuses `UPDATE` and `DELETE`. The Triage resource remains the source of truth for an Active Triage. A retention controller deletes a Triage seven days after `status.terminalAt`; the history stays. The Role therefore grants `delete` on Triages.
- **Metrics.** The server serves Prometheus metrics on `--metrics-bind-address` (port 9090). The Service exposes the `metrics` port, and the `ServiceMonitor` in `deploy/observability/monitors` scrapes it. The provisioned Grafana dashboard is in `deploy/observability/dashboards`.
- **Dashboard.** The server serves the embedded React dashboard and its read-only HTTP API on `--dashboard-bind-address` (port 8082); the Service exposes the `dashboard` port. The API reads Triages through the server's own client and appends nothing. `--grafana-url`, `--grafana-workload-dashboard-uid` and `--grafana-logs-dashboard-uid` configure the embedded Workload panels and their deep links; the Grafana base URL must be one the browser can reach, so it defaults to `http://localhost:3000` for the local port-forward. See [docs/dashboard.md](../../docs/dashboard.md).
- **Validation.** Scale, PatchResources, and Rollback are accepted only when `--sandbox-url` is set, and only for Workloads in the namespaces of `--patch-namespaces`; when `--sandbox-url` is empty, live-only `RestartWorkload` (for the `--patch-namespaces` namespaces) and `NoAction` work without a Sandbox. Each Workload that Scale, PatchResources, or Rollback targets names its manifest in the Sandbox with the `pagerless.dev/source-path` annotation. Scale renders the replica count, and PatchResources renders the container's requests and limits. Rollback reverts exactly one commit among the last 20 touching that path or a path in the Workload's `pagerless.dev/depends-on-paths` annotation, and only when the revert changes that one file. The server runs the `git` command line to read the Sandbox, so its image must include git. A Role in `sandbox` grants Workload reads and updates for Validation. The fail-closed `pagerless-server-dry-run-only` admission policy independently refuses every live Workload update from the server's service account, including subresources; only server-side dry runs are allowed. The ClusterRole grants read access to Nodes, whose allocatable values bound a PatchResources request when the Workload is unschedulable: the request must fit the largest node, and when the Sandbox repository has a `known-good` tag that declares a request for that resource, the request must not exceed that `known-good` value. Deploying to another Workload namespace requires the corresponding Role and RoleBinding there in addition to the flag. Deploying the server under a different namespace or service account also requires updating the admission policy's identity match.
- **Resource bounds.** `--patch-min-cpu`, `--patch-max-cpu`, `--patch-min-memory`, and `--patch-max-memory` set the bounds for requests and limits. Defaults are 10m–4 CPU and 16Mi–8Gi memory. Bounds must be positive Kubernetes quantities, with minimum no greater than maximum. `--scale-min-replicas` and `--scale-max-replicas` bound a Scale Proposal's replica count; defaults are 1–10.
- **Alert authentication.** The receiver requires a bearer token read from `--alertmanager-token-file` on every delivery. Bootstrap generates or reuses matching `pagerless-alertmanager` Secrets in `pagerless` and `monitoring`; Alertmanager reads its token from a mounted Secret file. An absent, unreadable, or empty expected token never permits an unauthenticated Trigger.
- **Approval.** A human approves or rejects by creating a `TriageApproval` in the `pagerless` namespace. A mutating webhook sets `spec.approver` from the admission request and overwrites any client-supplied value, and a validating webhook refuses a decision whose hash is not the current Proposal's, whose Triage is not Proposed, or whose Proposal is Stale or expired. Bootstrap binds `pagerless-approver` to the explicit current user returned by `kubectl auth whoami`; it refuses ServiceAccount and node identities and never grants an authenticated-user group. Existing user bindings are preserved. The server applies each accepted decision to the Triage's status.
- **Execution.** The server moves an Approved Triage to Executing, then asks `pagerless-executor` (`--executor-url`, by default the `pagerless-executor` Service in its own namespace) to execute it by Triage and Proposal hash. It authenticates with a projected service account token whose audience is `pagerless-executor`, read from `--executor-token-file` at every request. For a Proposal delivered by pull request, the server records the pull request URL, polls the Executor until the pull request merges, and then records the merge commit; Verification takes over from there. For RestartWorkload, the Executor executes live and the server records the pods it deleted. If the Executor refuses the Proposal or the pull request is closed without merging, the Triage ends as Failed. The server holds no GitHub write credentials; see `deploy/pagerless-executor`.
- **Other Approval clients.** The API requires the canonical resource name returned by `v1alpha1.TriageApprovalName`: it binds the Triage namespace, full name, UID, and exact Proposal hash. Approval and Rejection for that Proposal contend for the same name, so a second decision fails with AlreadyExists. An external client must compute that name before creating the resource; the CLI does this automatically. The server supplies `spec.approver` from the authenticated identity.
